# Load baseline — 2026-10-16 (P13-03)

**Relative baselines, not the binding numbers.** One Windows laptop runs everything: the stack in
Docker Desktop, the production Next server (`next build && next start`), the worker, and k6 2.3.0
in a container reaching the host at `host.docker.internal:3000`. There is no network, TLS or load
balancer in the path. The binding p95s are measured at the ALB at X-15. `LLM_ROUTE=fake`, so
generation time is pipeline overhead, not model time. 30 synthetic Pro users (`pnpm load:users 30`).

Re-run: see [`tests/load/README.md`](../../tests/load/README.md).

## CRUD — `pnpm load crud -- -e VUS=30 -e DURATION=2m`

30 virtual users, one account each. Each iteration is five reads, an `If-Match` settings write and
a job search, then a 2 s pause.

| Route class         | Requests | p95       | Budget (perf-budgets.json) |
| ------------------- | -------- | --------- | -------------------------- |
| `crud_read`         | 6,570    | 191 ms    | 300 ms ✓                   |
| `crud_write`        | 1,314    | 284 ms    | 500 ms ✓                   |
| `job_search_cached` | 1,314    | 332 ms    | 2,000 ms ✓                 |

9,198 requests at 75/s, **0 failed**.

## Generations — `pnpm load generations`

500 runs started across 30 users in 5 minutes (about 100 a minute, under each user's `ai` class).

| Measure                                  | Result                         |
| ---------------------------------------- | ------------------------------ |
| Starts answered 201                      | 500 / 500                      |
| `POST /generations` p95                  | 309 ms                         |
| Runs terminal afterwards                 | 500 / 500 `ready`, none stuck  |
| Start to `ready` (fake model)            | avg 1.6 s, p95 2.6 s           |
| Quota                                    | `used` = runs, `reserved` 0    |
| DLQs afterwards                          | generation DLQs empty          |

The k6 teardown that polls every run timed out at k6's 60 s default. It now has 8 minutes. The
terminal-state count above came from the database, which is authoritative anyway.

## SSE — `pnpm load sse` (worker stopped)

200 virtual users each started a run, which stayed queued with the worker stopped, and held its
event stream. Meanwhile 5 reads a second ran against the API.

| Measure                                 | Result                                    |
| --------------------------------------- | ----------------------------------------- |
| Streams opened (200, `text/event-stream`) | 100%                                    |
| Stream held                             | 5 min 1 s (the server's designed close), heartbeats received |
| Reads during the streams, p95           | 35 ms (budget 300 ms) ✓                   |
| Reads failed                            | 5 of 1,801 (0.28%)                        |

- **Deviation:** the plan says "200 streams held for 30 minutes". The server closes every stream at
  about 5 minutes by design, and clients reconnect with Last-Event-ID. Each stream was held for its
  whole life and reopened; the 200 were kept up for 6 minutes. A 30-minute hold is the same test
  with `-e DURATION=30m`.
- **The 5 failed reads were probably 429s, not verified.** All reads went to one account at 5/s,
  which is exactly the default class's 300 a minute. The script now spreads them over the accounts.
- **After the run:** the worker was restarted. 40 runs finished; the sweep failed the other 160 as
  `timed_out` with their quota released (they had waited past the generation timeout). None was
  left open or charged twice.

## What the load found and fixed

- **A malformed generation id answered 500.** `GET /generations/{id}`, `/result` and `/events`
  sent the raw string to a uuid column. They now answer 404 (existence hiding), and any other
  malformed literal (SQLSTATE 22P02) answers 400, never 500.
- **Pool exhaustion answered 500.** pg-pool's acquire timeout has no error code, so the 503
  mapping missed it. It now answers 503 `UNAVAILABLE` with `Retry-After`.
- **The first SSE attempt became a reconnect storm.** A stray worker finished the runs, so every
  stream closed at once and the virtual users reconnected without pause: 116k failed requests in
  6 minutes. The script now backs off after a short stream. Whether the apps' stream clients back off
  the same way is not checked here (toreview §105.20).
- **The production build was broken.** `next build` failed because `import.meta.dirname` is
  undefined in Next's server bundle (the recorded AI provider and Tesseract paths). Both now use
  `fileURLToPath(import.meta.url)`, like the other server modules. Development servers had hidden
  it.
