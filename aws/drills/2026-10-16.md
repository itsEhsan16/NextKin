# Drills — 2026-10-16 (P13 local hardening)

Local stack (`docker-compose.yml`, images pinned in `docker/versions.env`) on Windows 11 with Docker
Desktop. Synthetic data only (L4). These are the local twins of the cloud drills M5-14…M5-20, which
run again on AWS at X-15.

## Resilience (P13-02) — `pnpm drills`

Source: `packages/server/test/drills/resilience.drill.ts`. Each drill restarts or kills a real
piece of the stack, so they run on their own, not in the integration suite. 4/4 passed.

| Drill                    | What was done                                                       | Result                                                                                         |
| ------------------------ | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Worker killed mid-stage  | A real worker process (`dyingWorker.ts`) took a generation, hung in a stage, and was killed with SIGKILL | Another worker took the message after the visibility timeout and finished the run **7 s** after the kill. Charged once: `used 1, reserved 0` |
| Valkey restart           | `docker compose restart valkey` with a signed-in mobile session     | Healthy again in **6.9 s**. The old session answered **401** (not 500); signing in again worked; no durable data lost |
| Postgres restart         | `stop postgres`, a request, then `start postgres`                   | The request during the outage answered **503 UNAVAILABLE** with `Retry-After`. The pool recovered **1 s** after the start, with no process crash |
| ElasticMQ restart        | One generation published, one still in the outbox, then `restart elasticmq` | Healthy in **0.85 s**. The outbox republished the unsent message (1). The published-but-unconsumed message was lost; the sweep failed that run as `timed_out` with its quota released |

### What the drills found and fixed

- **A lost idle Postgres client crashed the process** (an unhandled pool `'error'` event, code
  57P01). Every pool now has an error handler: `src/db/database.ts`, the identity pool in
  `src/auth/build.ts`, and the deep health check.
- **A database outage answered 500 INTERNAL.** Connection-class errors (SQLSTATE class 08, 57P0x,
  ECONNREFUSED, ECONNRESET, ETIMEDOUT, EPIPE, "Connection terminated") now answer 503 UNAVAILABLE
  with `Retry-After: 5`.
- **The first kill drill was not a real kill.** An in-process worker's visibility heartbeat
  outlived its "death". The drill now uses a child process and SIGKILL.

### Local gaps, by design

- **Valkey runs without persistence**, so a restart signs everyone out. ElastiCache Serverless is
  replicated (X-05). The cloud drill re-checks that sessions survive a node failure.
- **ElasticMQ keeps queues in memory**, so a restart loses messages already published. The outbox
  and the 3-minute sweep make that a clean, retryable failure, never a hang or a double charge. SQS
  is durable (X-05).

## Degraded modes (P13-02, R-09) — `test/integration/degradedP13.int.test.ts`

Each dependency was forced to fail through its port:

| Capability | Forced failure              | API behaviour                                     | `/health/features` |
| ---------- | --------------------------- | ------------------------------------------------- | ------------------ |
| `ai`       | Every provider fails        | Assistant answers 503; generations fail, refunded | degraded           |
| `jobs`     | The job provider fails      | Search still answers 200 (cache or empty)         | degraded           |
| `payments` | The payment provider throws | Checkout answers 503 with a plain message; the plan is unchanged | degraded |
| `email`    | SMTP fails                  | A support ticket is still created (201); the failure is logged | degraded |

A healthy call clears its capability. Both apps show one banner while anything is degraded.

## Restore (P13-04) — `node scripts/drills/restore.mjs --volume 5000`

| Step                            | Time      |
| ------------------------------- | --------- |
| `pg_dump -Fc`                   | 1.0 s     |
| `createdb` + `pg_restore -j 4`  | 1.1 s     |
| Repoint and verify              | 0.6 s     |
| **Restore path total**          | **2.7 s** |

- Source database 99 MB; dump 12 MB.
- Row counts matched: users 5,127; resumes 25,101; versions 75,115; generations 20,097.
- The app role read the restored database under RLS.
- **Found:** restoring with `--no-owner --role=nextkin_owner` fails under FORCE RLS. The script
  restores as the superuser with ownership kept (see [the restore runbook](../runbooks/restore.md)).

Against the 1-hour RTO this is far inside budget at local volume. The cloud figure (an Aurora
point-in-time restore) is measured at X-15.

## DLQ replay (P13-05) — `test/integration/dlqP13.int.test.ts`

Inspection lists the dead letters without consuming them. A dry run changes nothing. A replay of
one type moves only that type back and leaves the rest. Generation replays reset the run to queued
with its checkpoint kept.
